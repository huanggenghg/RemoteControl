# AutoClick 旧版任务恢复体验设计

日期：2026-10-09，Asia/Shanghai。

状态：用户已在本聊天确认设计；设计与实现计划均已确认，当前目录实现及本地/现有模拟器验收已完成。用户选择“保存后保持停用，先试运行再手动启用”。本文件记录已确认的交互与其必要的保存约束。验收证据见 `.artifacts/autoclick-legacy-recovery/report.md`。

2026-10-10 用户追加要求“变动记得合并回main”。本次功能提交据此纳入本地 `main`，包含已验收的代码、测试、文档与复验运行器；原有其他修改保持原样，未推送或发布。

## 1. 目标与范围

在现有定时任务卡片中解释按钮不可用的原因，提供可以直接进入的重新录制流程，保留原任务直到新任务完整保存成功。沿用单个保存任务、现有墨绿主题、无障碍前置引导和悬浮录制界面。

旧版任务定义为：任务的点击、时间和星期仍可读取，但没有新版 `ClickRecordingProtection`。缺少的是每个点击对应的目标应用、录制时的屏幕尺寸和旋转方向。不能根据当前页面、当前屏幕或旧坐标猜测并补齐这些信息。

本次也落实此前提议的旧任务时间/星期编辑；这项操作保持停用，不能解除重新录制要求。范围为 `autoclick` 及必要的共享录制持久化接口。保留精确闹钟、五秒首次启动窗口、日期消费保护、试运行、紧急停止和普通有效任务的既有行为。

## 2. 原因说明与操作

旧任务卡片持续显示：

> 旧版任务需要重新录制，才能启用。
>
> 旧版没有保存点击对应的应用、屏幕尺寸和方向，无法校验点击环境。

原因直接可读，不能依赖点击已禁用的按钮或只显示“录制信息不完整”。现有恢复说明应与新入口使用一致文案，不能继续引导用户自行寻找“清空”。

有完整保护信息、只是历史执行遇到屏幕变化的任务，不归类为旧版任务；保留其现有录制说明和普通重新录制行为。本次新恢复入口针对缺少保护信息的旧任务。

| 情况 | 操作与说明 |
| --- | --- |
| 旧任务空闲、服务已连接 | “修改时间”“重新录制”“删除任务”可用；启用与试运行不可用，说明需要重新录制 |
| 保存中 | 禁止重复保存、取消及普通修改，显示“正在保存，请稍候” |
| 定时准备、倒计时、试运行或执行中 | 禁止编辑、录制及普通删除，显示具体执行状态；紧急停止保持可用 |
| 正在重新录制 | 禁止同时修改或替换原任务，显示“正在重新录制，请先保存或取消恢复”；允许继续录制及暂停恢复 |
| 无障碍未授权或未连接 | 复用现有前置引导；恢复会话及原任务保留，重新连接后可以继续 |

定时权限或时区异常应各自解释；不能用它们遮住旧任务缺少保护信息的原因。保存一个停用的新录制不要求定时权限。

## 3. 旧任务修改时间和星期

复用当前编辑弹框，预填原时间、星期和保存时区。取消不写入；无变更不替换身份。有效修改只更新时间、星期与任务回调身份，保留 `scheduleId`、旧点击、原时区、消费记录、最近结果和录制草稿。

保存后仍然停用，没有新闹钟；提示“时间已修改，旧版任务仍需重新录制”。保存失败保留原配置和最近结果。启用、试运行及真实手势入口继续要求有效保护信息，不能只放开按钮而绕过控制器检查。

## 4. 重新录制流程

1. 用户点击任务卡片的“重新录制”，打开说明弹框。说明如何在目标应用定位、轻点录制、长按设置时间，并说明“清空的是录制草稿，原任务会保留到新任务保存成功”。取消说明不会清空任何内容。
2. 确认开始后检查无障碍连接和悬浮权限。返回授权页后重新检查，不以打开设置页视为授权成功。权限满足、原任务身份仍一致，才建立恢复会话并开始空的新录制。
3. 恢复会话记录原任务身份、恢复会话 ID 和预先生成的新任务 ID；录制草稿记录同一个会话 ID。不能把此前的旧录制或另一次录制当成本次恢复结果。
4. 在目标应用录制点击。位置、间隔和保护信息作为同一份草稿保存；写入失败不能显示该点击已保存。中断后保留已经确认写入的草稿，可继续录制或重新开始。
5. 长按悬浮按钮打开设置面板，预填原时间和星期，明确新录制使用当前设备时区。按钮显示“保存并替换旧任务”。返回录制不会替换原任务。
6. 保存成功回到任务卡片，显示“重新录制已保存，任务仍停用。建议先试运行，再启用。”随后复用现有五秒试运行和手动启用入口。

取消恢复表示暂停该恢复流程，原任务仍在，已经录制的新草稿保留；再次进入提供“继续录制”与“重新开始”。只有明确选择重新开始才再次清空草稿。若原任务已删除或修改，草稿保留，但旧恢复会话不能覆盖变化后的任务，需重新进入并确认。

## 5. 保存成功与原任务保留

恢复保存使用独立于普通 `controller.save()` 的入口。现有普通保存会先替换任务再安排执行，不满足本次“失败时保留原任务、成功后保持停用”的要求。

保存前在现有串行修改边界及执行互斥内重读原任务、服务、录制会话、保护信息和执行状态。冻结不可变的新录制快照，校验点击数、时长、位置及保护信息对应关系。旧回调通过任务身份失效，不能覆盖新结果。紧急停止可以撤销保存的执行保留权；恢复保存永远不重新打开自动执行门。

**保存完成点是完整的新任务、有效保护信息和停用状态已经可靠落盘。** 完成点之前，原任务、原时间/星期、点击和最近结果仍是当前可读数据；完成点之后，新任务成为当前任务，`enabled=false`，没有待执行闹钟。

采用恢复专用的原子快照记录完成切换：先把原任务存储快照和完整的新停用任务写入受校验的原子记录，确认记录完整，再切换读取来源并同步回既有任务偏好文件。同步失败时，已确认的原子记录仍是权威读取来源，不能把完整保存误报为录制丢失，也不能让其他存储入口读取陈旧偏好。同步完成后才能清理记录。这样不依赖 `SharedPreferences.commit()` 失败时已改变的内存值，也不需要改变整个项目的存储格式。

全部任务存储读取、写入和观察必须经过同一个存储门面；临时原子记录有效时，后续修改也先保存该记录再同步，避免重启恢复出过期状态。原子文件写入必须检查同步与写后读回结果，不能把调用 `finishWrite()` 等同于确认成功。

新录制创建新 `id` 和 `scheduleId`；旧任务的执行结果不能归入新任务，新任务最初显示“尚无执行结果”。恢复前、取消和保存失败时，旧任务历史保持不变。成功不依赖是否具有定时权限，后续授权仍需用户手动启用。

## 6. 中断与重启

| 中断位置 | 恢复行为 |
| --- | --- |
| 说明或权限页 | 原任务与原录制不变，需明确开始后才清空草稿 |
| 录制或设置时间 | 原任务继续保留；读取匹配会话的新草稿，提供继续或重新开始 |
| 写入新任务完成点之前 | 原任务仍是当前任务；保留草稿，说明保存未完成并允许重试 |
| 新任务已落盘、提示或偏好同步尚未完成 | 认定新任务已保存，保持停用；完成同步或清理，不重新创建任务、不自动启用 |
| 无法确认存储记录完整 | 保留原偏好和原子记录，提示“保存状态未确认”；阻止替换与自动执行，不能宣称任务已保存或原任务已丢失 |

旋转、重复点击和回调重入只对应一个恢复会话及一个新任务身份。保存工作归 ViewModel 所有，工作协程不持有 Activity、View 或旧的设置面板。进程重启根据持久化完成记录恢复，不能根据内存中的 `saving` 判定成功。

## 7. 验收标准

- 旧版任务和有效停用任务分别验证，旧版原因与临时置灰原因准确；大字体、横屏仍可阅读和进入恢复。
- 旧任务时间/星期修改保持停用，原点击、草稿、时区、消费记录和最近结果保留；取消、无修改和写入失败均验证。
- 在说明取消、权限拒绝、草稿保存失败、无有效点击、保护不匹配、服务断连、原任务变化及新任务写入失败时核对原任务内容。
- 模拟偏好写入已改变内存却返回失败，仍从可靠快照读取正确任务；同步失败后新进程读取一致；清理记录失败不得回退旧任务或丢失后续修改。
- 重复保存、旋转、录制中退出及完成点前后进程结束均验证，区分真实进程恢复与仅重新构造存储对象。
- 成功后停用、无新闹钟、无自动点击；随后实际试运行一次，用户手动启用后才产生未来安排，旧事件不能执行。
- 回归有效任务编辑、试运行、紧急停止及精确定时，先保护模拟器原数据和权限，结束后核对恢复。

真机、厂商后台策略和实际系统重启验证继续单独记录；它们不阻止本次本地及现有模拟器可验证部分推进。设计确认不等于实现计划确认，本次不自动提交、推送或发布。
