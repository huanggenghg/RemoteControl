# AutoClick 秒级启动与超时跳过设计

日期：2026-10-07。范围：仅 AutoClick 及必要的共享执行接口。讨论中的方案、5 秒窗口、权限引导、恢复规则和验收标准已逐项获用户确认，完整设计文档也已获得整体确认。设计与实现计划均已获用户明确确认，当前已完成实现和模拟器验收（包括独立进程恢复及权限撤销/重授），详细证据和执行差异见实现计划末尾；未提交或推送。

## 1. 目标与边界

用户需要按指定时间开始真实点击。采用精确闹钟作为定时入口，目标是在计划时间后的 5 秒内发起第一下点击；错过窗口就跳过本次，后续计划继续。5 秒是本次已确认的业务规则，不是 Android 的平台保证。

保留单个已保存任务、星期选择、录制间隔、手动试运行、屏幕与目标应用检查、紧急停止及执行前持久化消费保护。任务编辑、多任务、提前待命模式、自动打开目标页面、自动解锁、迟到补执行及真机厂商策略验收不在本轮范围。

精确闹钟提高时间触发的适配性，不代表系统一定在窗口内送达，更不代表目标应用的业务操作已经成功。应用界面关闭后可以继续等待系统触发；强行停止应用后仍需用户重新打开并检查任务，不绕过 Android 限制。

## 2. 方案比较与选择

| 方案 | 特点 | 本轮结论 |
| --- | --- | --- |
| 精确闹钟触发后交给已连接的无障碍服务执行 | 新增必要的定时授权；第一下点击不再依赖后台工作队列的开始时间 | 用户已选择 |
| 增加提前待命模式 | 预先准备执行环境；增加待命操作、持续运行提示和资源消耗 | 暂不增加 |
| 保留 WorkManager 作为点击触发入口 | 改动较少，但调度时机不能满足本次秒级目标 | 替换旧入口 |

使用 `AlarmManager.setExactAndAllowWhileIdle()`、一次性 `PendingIntent` 和保存的时区计算下一次发生时间。每次只安排一个未来发生次数，不使用重复闹钟；收到本次事件后安排下一个未来时间。权限不足时不降级到 WorkManager 或非精确闹钟继续点击。

## 3. 五秒窗口的精确定义

设计划时间为 `T`，允许发起首手势的区间为 **`T <= firstDispatchAt < T + 5_000ms`**。例如 09:00:00 之前不点击，09:00:05 起不得发起第一下点击。

- 窗口包含闹钟送达、进程初始化、服务连接、停止按钮准备、环境核验、消费记录落盘及第一点本身的等待。不能从接收闹钟或连接成功时重新计时。
- 服务尚在连接时，可以使用窗口剩余时间等待；授权关闭则立即失败。原先后台等待最多 10 秒的规则不能让本次定时点击越过 5 秒截止。
- 保留录制时间间隔，不新增定时执行倒计时。若第一点有等待，该等待也受启动截止约束；手动试运行仍使用原有 5 秒倒计时，不受本次定时窗口规则影响。
- 首手势的最终时间检查放在真正调用 Android 手势接口之前，覆盖现有执行器内部的延迟。不能仅以取得执行权、开始协程或显示停止按钮作为已经开始点击。
- 窗口内已经发起首手势后，其余点击按录制间隔继续；不要求整个序列在 5 秒内结束。后续仍逐点检查环境、时间变化、服务身份、任务身份和停止状态。
- 消费落盘后、首手势前如果发生超时或取消，允许本次零点击，但不得再次领取或重放。磁盘保存失败时不得发起手势。
- 等待和执行同时保留墙上时间与单调时钟锚点，沿用现有时钟变化保护；收到系统时间变化或检测到异常时停止本次，不能因时间回拨延长窗口。

`firstDispatchAt` 是应用向系统发起首手势的时间；真实触摸由 Android 投递。验收同时记录目标按钮收到点击的时间，分别报告两者，不把请求已提交写成目标业务已完成。

## 4. 权限及用户操作

无障碍继续作为整个应用的前置条件，使用已实现的自动检查与开启/退出引导。精确定时权限只限制定时任务，录制与手动试运行仍可使用。

| 情况 | 行为与文案 |
| --- | --- |
| 保存或启用定时任务，但系统要求的定时权限未开启 | 保留录制与任务配置，任务不进入启用状态；说明“定时点击需要开启闹钟和提醒权限”，提供“去开启 / 暂不” |
| 从设置返回，权限已授予 | 回到任务页，由用户明确点击“启用任务”；不因授权成功自动开始本次或恢复旧调度 |
| 已有任务失去权限 | 当前状态显示“定时权限未开启”；保留内容，不显示已成功安排下一次，不通过其他入口补执行 |
| 重新授予权限 | 仍需用户明确启用；只安排严格晚于当前时间的下一次计划 |
| 授权检查通过，但实际安排抛出安全或系统异常 | 任务显示“定时安排失败，请重新启用”，不伪装成功；不影响录制和手动试运行 |

Android 12 及以上按实际系统能力检查 `canScheduleExactAlarms()`，使用 `SCHEDULE_EXACT_ALARM` 和用户设置入口；不选择自动授权且用途受限的 `USE_EXACT_ALARM`。较旧系统不显示不存在的授权入口。

系统可在撤权时终止应用并取消闹钟，因此不依赖撤权瞬间执行代码更新界面或写记录。前台检查、下一次启动及权限变化处理统一校验真实能力；重新授权事件不能直接重建启用状态。启动协调不得在权限事件处理前无条件恢复点击调度。

到点仍要求屏幕亮着且已解锁、目标应用匹配、停止按钮可用、录制显示信息匹配。锁屏或目标应用不匹配时立即跳过，页面布局是否仍适合点击仍由用户负责；应用匹配不能证明同一应用内的页面内容未变化。

## 5. 组件与执行归属

| 组件 | 职责 |
| --- | --- |
| 定时策略 | 计算下一次未来时间，判断早到、窗口内、超时、时区变化及已终结发生次数；可注入时间测试 |
| 精确闹钟调度器 | 检查权限，持久化并安排/替换/取消下一次一次性闹钟，返回实际安排结果 |
| 闹钟接收器 | 校验事件与当前任务身份，拒绝旧事件；在剩余窗口内等待服务连接并交接；推进下一次安排 |
| 定时执行器 | 复用现有安全执行步骤，取得与试运行共享的执行权、准备停止控件、持久化消费并逐点检查 |
| 任务存储与控制器 | 串行协调用户操作、迁移、恢复、调度状态、发生次数终结及结果记录 |
| 系统恢复接收器 | 处理启动完成、应用更新、系统时间/时区及授权变化；只恢复允许恢复的未来计划 |
| 状态观察器与任务卡片 | 读取新的调度事实、权限、执行会话与历史结果，保留当前状态/最近结果分区 |

链路为：保存/启用 → 持久化配置及下一次意图 → 安排精确闹钟 → 接收器核验 → 已连接无障碍服务的生命周期协程执行 → 记录结果。安排下一次不能成为首手势之前的长队列；调度推进与执行交接都须保证窗口检查和失败闭环。

接收器的异步处理只承担短时核验、连接等待、交接和状态落盘。长点击序列由无障碍服务生命周期拥有；服务销毁会取消序列，不让接收器或 Application 的常驻协程承载最长八分钟的执行。不新增前台待命服务或持续待命通知，不经过 Activity 启动点击，不把首手势重新交给 WorkManager 排队。

共享库只提供通用手势和服务生命周期能力，不引用 AutoClick 的任务或调度实现。现有 Worker 中与具体后台入口无关的执行保护提取到 AutoClick 内的定时执行器，手动试运行继续共用互斥执行和停止机制。

## 6. 调度状态与防重复

保存的任务内容、是否允许定时、下一次安排及当前执行记录分开。至少持久化调度版本、配置身份、启用代次、下一次计划时间、安排状态和对应事件身份；“已安排”只表示系统 API 已接受，不是一定会准时到达。

- 事件身份绑定任务、启用代次、调度版本和计划时间。停用/重新启用产生新代次，旧广播及旧执行回调不得修改新任务或发起点击。
- 使用不可变、显式指向自有接收器的 PendingIntent；身份不能仅放 extras，避免替换时复用错误事件。接收入口不接受外部应用任意指定点击任务。
- 当前发生次数和下一次安排独立存储。已经安排明天不等于今天已结束；今天的结果也不得覆盖明天的计划。
- 继续保留执行前持久化消费保护；另外持久化已跳过/已终结的发生次数边界。相同计划停用再启用保留这些边界，系统时间回拨也不得重放此前已执行或已跳过的发生次数。
- 重复事件只处理一次。正在手动试运行或其他点击序列占用执行权时，本次定时跳过，不排队等待，不抢占试运行。
- 早到事件不点击，也不能将尚未到来的发生次数记为跳过；只在身份仍有效时保证原计划的未来安排。
- 控制器、接收器和恢复入口通过同一串行修改边界协调。系统闹钟与本地存储无法组成一笔事务，安排失败或进程中断必须可识别为“安排未确认/失败”；旧事件依靠身份与终结记录失效，不能据存储意图声称闹钟必然存在。
- 普通冷启动只校验、迁移和呈现实际可确认状态，不因缺少已确认的安排就静默恢复一个已经被系统取消的任务；安排未确认时引导用户明确重新启用。显式启用、合法的下一次推进及系统恢复入口负责重建未来安排。
- 本次提前终止不取消后续计划；下一次安排失败则明确提示修复调度。紧急停止、用户停用、删除或替换任务会先阻止继续点击，并取消对应的未来闹钟。

一次序列中断后仍不自动重放已完成点击。启用/停用控制结果与执行结果分开，不覆盖上一条真实执行记录。

## 7. 恢复与迁移

| 事件 | 处理 |
| --- | --- |
| 普通进程回收 | 已由系统接受的闹钟仍作为入口；启动执行仍须在原窗口内连接服务并通过保护，不保证冷启动一定赶上 |
| 手机重启 | 接收启动完成后，已有新版本且允许启用的任务在权限齐备时重建未来安排；错过的已保存发生次数终结为跳过；不补点，不主动打开目标应用 |
| 应用更新 | 已迁移的新版本任务按相同恢复规则处理；旧版任务走下述首次迁移 |
| 系统时间调整 | 取消旧安排并计算严格未来的下一次；正在执行/准备的本次停止，已终结边界保留 |
| 时区改变 | 暂停调度，显示“时区已改变，需重新设置任务”，沿用重新保存任务的现有路径；不新增任务编辑功能 |
| 授权重新授予 | 更新可用能力与引导，不自动恢复；用户启用后安排下一次未来时间 |
| 删除/停用/替换/紧急停止 | 取消未来闹钟，失效旧事件，执行中的序列沿用现有取消保护 |

首次迁移必须先取消原唯一 WorkManager 任务，保留录制、配置、消费保护和最近结果，任务进入“定时方式已更新，请启用任务”。需重新录制的旧任务继续沿用现有保护要求。用户明确启用时才登记新闹钟。

旧 Worker 保留不可发起点击的兼容入口，防止升级时残留工作或取消竞争进入旧的十五分钟执行路径。新的定时执行全部使用五秒规则；不保留另一条可执行的迟到路径。迁移标记只有在持久化和旧入口阻断均成功后才视为完成；失败时展示无法启用，允许用户重试。

对多次启动或重复恢复事件保持幂等。重启恢复只面向原本已明确启用的新版本任务；待授权、待迁移确认、时区待处理或用户停用的任务不得因重启自动启用。

## 8. 状态和结果文案

保留现有卡片结构，通过精确调度记录替换 WorkInfo 作为下一次安排来源。不存在可靠安排时不根据任务时间单独推断“已安排”。不再显示分钟级等待或原十五分钟截止文案。

| 状态 | 示例 |
| --- | --- |
| 已安排未来时间 | 下次：今天（周三）09:00；可展开说明“需在启动窗口内满足执行条件” |
| 正在窗口内连接/核验 | 执行准备中 |
| 首手势已开始 | 定时执行 1 / N |
| 五秒窗口已过 | 已错过启动时间，本次跳过；下一次时间另行显示 |
| 缺少权限 | 定时权限未开启；去开启，返回后启用任务 |
| 安排失败或无法确认 | 定时安排失败，请重新启用 / 暂无法确认下一次计划 |
| 升级待启用 | 定时方式已更新，请启用任务 |

最近结果独立记录发生时间、结果时间和明确原因：启动超时、服务未连接、无障碍关闭、锁屏、目标应用不匹配、停止控件不可用、正在执行其他点击、时钟改变、手势失败、取消或完成。没有收到闹钟而在恢复时发现过期，只记录“已错过启动时间”，不猜测系统未送达的原因。

保存启动诊断时间：计划时间、接收事件时间、首手势发起时间；真机之外仅测试目标能记录按钮收到时间。诊断数据不包含目标页面文本、账号内容或其他敏感资料，不把开发诊断字段全部放入用户主界面。

## 9. 验收标准

### 纯逻辑与存储回归

- 时间边界覆盖 `T-1ms`、`T`、`T+4_999ms`、`T+5_000ms`、跨日、跨周、时区与时钟变化；等待、停止控件准备和执行器内第一点延迟均不能延长窗口。
- 跨进程重建后的消费/跳过保护、停用再启用、重复事件、旧代次回调、替换任务及调度落盘失败均不得重复开始。
- 覆盖事件未收到后的过期恢复，验证不会把历史结果归为当前发生次数，不伪造超时的系统原因；下一次安排与本次结果独立。
- 权限关闭/重授、启动与授权事件的处理顺序、迁移中断重试、重启/应用更新恢复和旧 Worker 竞争均有明确断言。

### 现有模拟器短时验收

- 正常任务通过实际保存/启用入口安排到下一分钟，保留五秒保存余量，单次等待上限 90 秒；真实按钮只收到一次点击。记录计划、广播、首手势与按钮接收时间，正常场景要求首手势及按钮接收均落在五秒窗口内。
- 通过测试夹具延迟交接或发送可验证身份的过期事件超过五秒，断言零手势、零按钮点击、正确跳过结果及下一次未来安排；不修改生产窗口或生产时钟来获得通过。
- 覆盖授权拒绝、撤销与重授，连接在剩余窗口内恢复以及窗口耗尽、锁屏、错误目标应用、停止按钮准备、首手势前取消、序列中紧急停止、试运行互斥、任务替换和重复事件。
- 验证旧工作取消且无法点击，启用新调度需要明确操作；试运行保留倒计时且不消费定时发生次数。
- 重启恢复以纯策略、存储重建及模拟系统恢复入口测试为基础；实际重启和进程重启实验独立记录是否运行，不把模拟事件称为真实重启验收。不为常规回归冷启动另一台模拟器。
- 设备测试前快照应用数据及实际影响的系统授权，结束后恢复并核对任务与权限；保留失败日志及截图。真实运行时的模拟器系统阻塞单独报告，不削弱五秒验收条件。

### 工程检查与交付

使用 Android Studio 的 JDK，运行受影响 JVM 测试、AutoClick debug/test APK 构建、Android Lint、设备回归及 diff 检查；报告确切通过数和剩余警告。验收报告区分逻辑测试、真实闹钟触发、真实按钮点击、模拟恢复和实际重启。真机厂商后台限制仍未覆盖，不把模拟器一次达标宣传为全设备时间保证。
